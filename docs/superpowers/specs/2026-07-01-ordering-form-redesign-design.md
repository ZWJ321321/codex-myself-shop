# 订餐表单与下单协议重做设计

- 日期：2026-07-01
- 项目：`E:\餐厅介绍`
- 范围：仅重做前端下单表单及其对应前后端协议，不重做整站品牌展示结构
- 已确认方向：固定菜单下单、完整型表单、前端实时计算总价、后端复算并确认、MySQL 作为默认数据库

## 1. 背景

当前仓库已经从静态餐厅页迁移为 `Vue 3 + Vite` 前端，并补入了一套 Django 点餐后端。现有下单实现可以完成最基础的点菜和提交，但表单字段过少，提交流程过于直接，无法承载“取餐时间、用餐方式、价格确认”这些真实下单所需信息。

本次不推翻整个站点视觉内容，也不重做品牌介绍、故事、空间环境等展示区块。重做重点只放在“提交表单这一块”，并且同步重做表单调用的协议，使它从轻量演示升级成一个更完整的订餐下单流程。

同时，本次不采用“在旧表单上打补丁”的方式。现有下单区视为旧版本，前端页面结构、状态流、接口调用和后端协议都按整体替换思路重做。

## 2. 目标

- 将现有“直接提交”改为“先确认价格，再正式下单”的两段式流程。
- 将表单补齐为完整型固定菜单下单：菜品、数量、姓名、电话、取餐时间、用餐方式、备注、总价确认。
- 保持前端实时展示预计总价，但以后端复算结果作为确认价和最终落单依据。
- 重做前后端协议，使字段、错误码和状态流清晰可测。
- 采用 MySQL 作为默认数据库，而不是以本地轻量数据库为设计基准。
- 尽量复用现有 `Dish`、`Order`、`OrderItem` 的主体结构，只调整必要字段和接口。

## 3. 非目标

- 不重做首页其余品牌展示内容。
- 不新增在线支付、优惠券、库存扣减、会员体系。
- 不改成套餐式或自定义询价式下单。
- 不为本次设计引入复杂的报价单令牌、会话购物车或用户账户系统。
- 不把数据库密码写入仓库文档、源码或受版本控制的配置文件。

## 4. 方案选择

候选方向有三种：

- 单接口直接下单：实现快，但“价格确认”仍然混在提交动作里，体验不清晰。
- 两段式下单：先预览确认，再正式落单，能明确区分预计价格、确认价格和最终订单。
- 报价单令牌式下单：最严谨，但对当前项目明显偏重。

最终采用第二种：两段式下单。

原因如下：

- 与“前端实时计算，后端复算”的规则最一致。
- 用户可以看到后端确认后的标准化明细，而不是只依赖前端购物车。
- 可以为后续价格变动、菜品下架、重新确认等业务错误留下稳定处理路径。

## 5. 用户流程

新下单流程固定为以下两步：

1. 用户选菜、改数量、填写联系人和取餐信息，页面实时显示前端估算总价。
2. 用户点击“确认订单信息”，前端调用预览接口，后端按当前菜单复算并返回标准化明细和确认总价。
3. 用户检查确认区内容后，点击“正式下单”，前端再调用正式创建接口。
4. 后端再次复算；若金额一致则创建订单，若金额变化则要求用户重新确认。
5. 提交成功后，页面展示完整订单回执。

该流程的核心约束是：前端展示的总价只是即时估算，真正的确认价以后端预览返回值为准；正式落单时后端仍然不信任前端价格。

## 6. 协议设计

### 6.1 预览接口

- 方法：`POST`
- 路径：`/api/order-previews`

请求体：

```json
{
  "customer_name": "张三",
  "phone": "13800138000",
  "pickup_time": "2026-07-01T18:30",
  "dining_mode": "takeaway",
  "note": "少辣，不要香菜",
  "items": [
    { "dish_id": 3, "quantity": 2 },
    { "dish_id": 7, "quantity": 1 }
  ]
}
```

成功返回：

```json
{
  "code": "ok",
  "message": "success",
  "data": {
    "customer_name": "张三",
    "phone": "13800138000",
    "pickup_time": "2026-07-01T18:30",
    "dining_mode": "takeaway",
    "note": "少辣，不要香菜",
    "items": [
      {
        "dish_id": 3,
        "dish_name": "招牌烤鸡",
        "unit_price": "68.00",
        "quantity": 2,
        "line_total": "136.00"
      }
    ],
    "total_amount": "136.00"
  }
}
```

职责：

- 校验联系人信息、取餐信息、菜品列表是否合法。
- 按后端当前菜单复算每项小计和总价。
- 返回用于展示确认区的标准化订单摘要。

### 6.2 正式下单接口

- 方法：`POST`
- 路径：`/api/orders`

请求体与预览接口基本一致，但额外带上用户确认过的总价：

```json
{
  "customer_name": "张三",
  "phone": "13800138000",
  "pickup_time": "2026-07-01T18:30",
  "dining_mode": "takeaway",
  "note": "少辣，不要香菜",
  "expected_total_amount": "136.00",
  "items": [
    { "dish_id": 3, "quantity": 2 },
    { "dish_id": 7, "quantity": 1 }
  ]
}
```

成功返回：

```json
{
  "code": "ok",
  "message": "success",
  "data": {
    "order_no": "OD202607010001",
    "customer_name": "张三",
    "phone": "13800138000",
    "pickup_time": "2026-07-01T18:30",
    "dining_mode": "takeaway",
    "note": "少辣，不要香菜",
    "items": [
      {
        "dish_id": 3,
        "dish_name": "招牌烤鸡",
        "unit_price": "68.00",
        "quantity": 2,
        "line_total": "136.00"
      }
    ],
    "total_amount": "136.00"
  }
}
```

职责：

- 再次按后端菜单复算订单。
- 若复算总价与 `expected_total_amount` 一致，则创建 `Order` 和 `OrderItem`。
- 若不一致，则返回 `price_changed` 错误码，并附带最新摘要，要求前端重新确认。

## 7. 数据字段与模型调整

### 7.1 表单字段

前端下单表单固定包含：

- `customer_name`
- `phone`
- `pickup_time`
- `dining_mode`
- `note`
- `items`

其中 `items` 为固定菜单下单的菜品数组，每项包含：

- `dish_id`
- `quantity`

### 7.2 Order 模型

现有 `Order` 主体保留，但新增以下字段：

- `pickup_time`
- `dining_mode`

保留并继续使用的字段：

- `order_no`
- `customer_name`
- `phone`
- `note`
- `status`
- `total_amount`

`dining_mode` 建议使用枚举值，例如：

- `takeaway`
- `dine_in`

### 7.3 OrderItem 模型

现有 `OrderItem` 快照思路保留，不推翻结构。继续保存：

- 菜品关联
- 菜名快照
- 单价快照
- 数量
- 小计

原因是订单一旦创建，后续菜名或价格变更不应污染历史订单。

## 8. MySQL 设计前提

- Django 默认数据库为 MySQL。
- 字符集统一按 `utf8mb4` 设计，排序规则使用 MySQL 8 的常规中文兼容方案。
- 金额字段继续使用 `DecimalField`，不使用浮点型。
- 时间字段、状态字段、订单号索引都以 MySQL 8 能力为基准设计和测试。
- 后续数据库连接信息应放入本地环境变量或未纳入版本控制的配置文件，不写入仓库中的公开文档和源码常量。

## 9. 校验规则

### 9.1 前端校验

进入预览请求前，前端至少校验：

- 必须至少选择一道菜。
- `customer_name` 必填。
- `phone` 必填且格式合法。
- `pickup_time` 必填。
- `dining_mode` 必填。
- 每个菜品数量必须大于 0。

前端校验目标是改善体验，而不是替代后端安全校验。

### 9.2 后端校验

预览和正式下单都必须重新校验：

- 菜品存在。
- 菜品可售。
- 菜品所属分类可用。
- 数量为正整数。
- `customer_name` 非空。
- `phone` 非空且格式合法。
- `pickup_time` 非空且不能早于当前时间。
- `dining_mode` 为允许的枚举值。

### 9.3 价格变动校验

正式下单时，后端必须将复算总价与前端提交的 `expected_total_amount` 比较：

- 一致：允许创建订单。
- 不一致：拒绝创建，并返回 `price_changed`。

`price_changed` 返回体应包含最新 `items` 与 `total_amount`，用于前端直接刷新确认区。

## 10. 前端页面与状态流

### 10.1 页面结构

下单页在视觉上仍可保持单页，但内部拆成四块：

- 菜单选择区
- 订单信息区
- 价格确认区
- 提交成功区

不再沿用现有“购物车 + 表单 + 直接提交”的轻量演示结构，而是整体替换为确认驱动的流程页。

### 10.2 状态阶段

前端状态流固定为：

- `editing`
- `previewing`
- `preview_ready`
- `submitting`
- `success`

### 10.3 状态失效规则

一旦用户在预览成功后修改以下任一内容，当前确认结果立即失效，页面回退到 `editing`：

- 菜品选择
- 菜品数量
- 取餐时间
- 用餐方式
- 备注
- 联系人姓名
- 手机号

同时页面提示：“订单信息已变更，请重新确认价格。”

### 10.4 错误处理

- 菜单加载失败：展示独立错误提示，保留页面结构。
- 表单校验失败：在字段下方显示错误，不发预览请求。
- 预览失败：保留用户已填内容，展示字段错误或业务错误。
- 正式下单失败且错误码为 `price_changed`：刷新确认区，要求重新确认。
- 正式下单普通失败：停留在确认态，允许用户重试。

### 10.5 成功态

下单成功后不只显示一句成功提示，而是展示订单回执卡片，包含：

- 订单号
- 联系人
- 手机号
- 取餐时间
- 用餐方式
- 菜品明细
- 最终总价
- 备注

## 11. 接口错误约定

统一响应结构继续沿用：

```json
{
  "code": "validation_error",
  "message": "提交数据不合法",
  "errors": {
    "phone": ["手机号格式不正确"]
  }
}
```

本次新增并明确使用的业务错误码：

- `validation_error`
- `price_changed`

其中：

- `validation_error` 用于字段、菜品、时间等输入不合法。
- `price_changed` 用于用户确认后的价格已失效，需要重新确认。

## 12. 实现边界

本次协议重做应优先复用现有基础，而不是彻底新起炉灶：

- 复用现有 `Dish` 查询和后端复算逻辑骨架。
- 复用现有 `Order` / `OrderItem` 主表与快照模型思路。
- 重写前端下单区的页面结构、状态机和接口调用方式。
- 重写后端订单协议、字段校验和错误码约定。
- 数据库落地目标是 MySQL，而不是仅在本地临时数据库上跑通。

这意味着“推翻重做”只针对下单表单和协议，不针对整个仓库结构。

## 13. 测试范围

前端至少覆盖：

- 缺字段时不能进入预览。
- 预览成功后修改关键字段会使确认失效。
- `price_changed` 返回后不能继续用旧确认直接提交。
- 下单成功后展示完整订单回执。

后端至少覆盖：

- 预览接口能按菜品与数量复算总价。
- 正式下单能成功创建订单及订单项。
- 空购物车、无效手机号、非法时间、非法用餐方式会被拒绝。
- 菜品下架或分类不可用时会被拒绝。
- `expected_total_amount` 不匹配时返回 `price_changed`。
- MySQL 下中文字段、备注和订单快照能正常持久化。

## 14. 设计结论

本次重做采用“固定菜单下单 + 完整型表单 + 两段式下单协议 + MySQL 默认数据库”的方案。

用户先编辑订单，再通过后端预览确认价格，最后正式提交。前端负责即时反馈与状态管理，后端负责复算、校验和最终订单事实。这样既能把现有演示型表单彻底升级，又不会把整个餐厅介绍页一并推翻。

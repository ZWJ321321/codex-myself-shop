# Django 点菜后端设计

- 日期：2026-07-01
- 项目：`E:\餐厅介绍`
- 前端现状：Vue 3 + Vite 单页餐厅介绍站
- 设计范围：为现有单页补充点菜能力，采用 Django 作为后端

## 1. 背景

当前项目是一个以品牌展示为主的 Vue 单页网站，页面已经包含首屏、品牌故事、招牌菜、空间环境、亮点和联系信息等区块。现有菜品内容写在前端静态数据中，只能展示，不能完成真实下单。

本次新增一个轻量版点菜闭环，目标是在不推翻现有前端结构的前提下，让用户可以在同一页面中浏览菜单、加入购物车、填写基础信息并提交订单，同时让商家能够在 Django admin 中查看和管理订单。

## 2. 目标

本次设计的目标如下：

- 在现有单页中新增在线点菜区块，不跳转独立点餐页。
- 后端提供菜品与订单 API。
- 用户无需注册登录。
- 下单字段只包含姓名、手机号、备注。
- 商家使用 Django admin 管理分类、菜品和订单。
- 保持当前页面的品牌展示属性，不破坏已有滚动导航与渐入效果。

## 3. 非目标

本次不包含以下内容：

- 用户注册、登录、会员体系
- 在线支付
- 桌号、堂食扫码、自取时间选择
- 优惠券、积分、库存扣减
- 商家自定义后台页面
- 复杂促销规则和配送能力

这些能力如果后续需要，应在现有模型和接口基础上单独扩展，不在本次首版中提前实现。

## 4. 总体方案

采用“Vue 单页前端 + Django API 后端”的分层方案。

- 前端继续使用现有 Vue 3 + Vite 项目，保留当前介绍页结构。
- 后端新增独立 Django 工程，负责菜单数据、订单写入、基础校验和后台管理。
- 点菜功能作为当前单页中的新增区块嵌入，而不是新开 `/order` 页面。
- 购物车状态保留在前端本地状态中，不存入 Django session。
- 正式下单时以后端数据库中的菜品状态和价格为准。

这种方案可以在不改变现有前端栈的情况下补齐业务闭环，并且为后续增加订单状态、桌号或支付功能保留扩展空间。

## 5. 目录结构

建议在当前仓库下新增独立后端目录：

```text
E:\餐厅介绍
├─ backend/
│  ├─ manage.py
│  ├─ config/
│  │  ├─ __init__.py
│  │  ├─ settings.py
│  │  ├─ urls.py
│  │  ├─ asgi.py
│  │  └─ wsgi.py
│  └─ apps/
│     ├─ common/
│     ├─ catalog/
│     └─ orders/
├─ src/
├─ index.html
├─ package.json
└─ vite.config.js
```

目录原则如下：

- `src/` 继续承载现有 Vue 页面。
- `backend/` 完整隔离 Django 代码，避免 Python 和 Vite 入口混杂。
- `apps/catalog` 负责菜单域模型。
- `apps/orders` 负责订单域模型与下单接口。
- `apps/common` 存放可复用的公共逻辑，例如时间字段或通用响应封装。

## 6. 前端集成方式

点菜功能将直接嵌入现有单页，而不是新增单独路由页面。

推荐区块顺序：

1. 保留原有 Hero、品牌故事、招牌菜等展示内容。
2. 在“招牌菜”之后、“联系信息”之前插入“在线点菜”区块。
3. 在线点菜区块内部包含菜单列表、购物车摘要和提交订单表单。
4. 成功下单后在当前页面展示订单编号和成功提示。

前端体验目标如下：

- 菜品按分类展示。
- 用户可对菜品执行“加入购物车”。
- 用户可在购物车中增加数量、减少数量和删除条目。
- 页面实时显示合计金额。
- 用户填写姓名、手机号和备注后提交订单。
- 接口失败时前端显示明确的错误提示。

首版不要求复杂状态管理库。购物车和菜单数据可由 `App.vue` 内部状态管理，后续如果组件拆分再考虑抽离。

## 7. Django 应用划分

### 7.1 catalog

职责：

- 菜品分类管理
- 菜品管理
- 提供前端读取分类和菜品的只读接口

### 7.2 orders

职责：

- 订单创建
- 订单项快照保存
- 订单状态管理
- 下单预校验与正式提交接口

### 7.3 common

职责：

- 公共模型基类
- 公共校验工具
- API 统一响应格式

## 8. 数据模型设计

### 8.1 Category

字段建议：

- `name`：分类名称
- `slug`：分类标识，供接口筛选与前端稳定引用
- `sort_order`：排序值，数值越小越靠前
- `is_active`：是否启用
- `created_at`
- `updated_at`

说明：

- `slug` 应唯一，避免以后端中文名称作为接口筛选参数。
- 分类停用后，不应继续在前台菜单中展示。

### 8.2 Dish

字段建议：

- `category`：外键，关联 `Category`
- `name`：菜名
- `description`：菜品描述
- `price`：菜品价格，使用 `Decimal`
- `image_url`：菜品图片地址
- `is_available`：是否可点
- `sort_order`：排序值
- `created_at`
- `updated_at`

说明：

- 首版使用 `image_url` 而不是 Django 文件上传，降低媒体存储复杂度。
- `is_available` 用于临时下架，已下架菜品不应接受下单。

### 8.3 Order

字段建议：

- `order_no`：业务订单号，唯一
- `customer_name`：客户姓名
- `phone`：手机号
- `note`：备注，可空
- `status`：订单状态
- `total_amount`：订单总金额
- `created_at`
- `updated_at`

状态建议：

- `pending`：待处理
- `confirmed`：已确认
- `completed`：已完成
- `cancelled`：已取消

说明：

- `order_no` 需要业务可读，便于后台和电话沟通。
- `total_amount` 由后端汇总计算，不信任前端传值。

### 8.4 OrderItem

字段建议：

- `order`：外键，关联 `Order`
- `dish`：外键，关联 `Dish`
- `dish_name_snapshot`：下单时菜名快照
- `unit_price_snapshot`：下单时单价快照
- `quantity`：数量
- `line_total`：小计金额

说明：

- 快照字段必须保留，避免后续修改菜名或价格污染历史订单。
- `line_total` 由后端根据单价和数量计算并持久化。

## 9. 订单编号规则

首版建议使用“日期 + 递增序号”的可读编号，例如：

`OD202607010001`

规则要求：

- 同一订单号全局唯一。
- 生成逻辑放在后端。
- 不要求分布式复杂生成器，但要避免简单时间戳带来的可读性差和碰撞风险。

首版可在事务中基于日期生成递增编号；如果后续并发量显著上升，再调整实现。

## 10. API 设计

首版建议提供以下接口。

### 10.1 获取分类

- 方法：`GET`
- 路径：`/api/categories/`

行为：

- 返回启用中的分类列表。
- 按 `sort_order` 排序。

用途：

- 前端渲染菜单分类导航或分类标题。

### 10.2 获取菜品

- 方法：`GET`
- 路径：`/api/dishes/`

建议支持参数：

- `category`：可选，按分类 `slug` 过滤

行为：

- 返回可展示的菜品列表。
- 默认只返回可点菜品。
- 按分类和排序值输出。

### 10.3 订单预校验

- 方法：`POST`
- 路径：`/api/orders/preview/`

输入：

- `items`
  - `dish_id`
  - `quantity`

行为：

- 校验每个菜品是否存在、是否可点、数量是否合法。
- 以后端价格重新计算总金额。
- 返回标准化后的订单项和总金额。

意义：

- 前端可以在正式提交前获得准确金额。
- 即使前端本地价格或数据滞后，后端也能给出最终确认结果。

该接口不是绝对必须，但建议首版保留，便于后续扩展确认弹层或二次确认。

### 10.4 创建订单

- 方法：`POST`
- 路径：`/api/orders/`

输入：

- `customer_name`
- `phone`
- `note`
- `items`
  - `dish_id`
  - `quantity`

行为：

- 校验姓名、手机号和购物车非空。
- 校验菜品存在且可点。
- 校验数量为正整数。
- 以后端价格重新计算总金额。
- 在事务中创建 `Order` 与 `OrderItem`。
- 返回订单号、总金额和订单摘要。

创建订单时不接受前端直接提交的总价作为可信值。

## 11. API 响应约定

建议统一响应结构，便于前端稳定处理：

成功示例：

```json
{
  "code": "ok",
  "message": "success",
  "data": {}
}
```

失败示例：

```json
{
  "code": "validation_error",
  "message": "提交数据不合法",
  "errors": {
    "phone": ["手机号格式不正确"]
  }
}
```

约束：

- `message` 用于用户可感知提示或日志定位。
- `errors` 用于表单字段级错误展示。
- 业务失败要有稳定的 `code`，不要只返回自由文本。

## 12. 校验规则

### 12.1 前端校验

前端在提交前至少校验：

- 购物车不能为空
- 姓名不能为空
- 手机号不能为空
- 手机号格式基础合法

前端校验的目标是优化体验，而不是替代后端安全校验。

### 12.2 后端校验

后端必须再次校验：

- 菜品存在
- 菜品处于可点状态
- 数量是大于 0 的整数
- `customer_name` 非空
- `phone` 非空且格式合法

如果某个菜在用户加入购物车后被后台下架，正式下单时必须阻止创建订单，并返回明确错误信息。

## 13. 事务与一致性

正式下单必须放在数据库事务中执行。

事务内至少包含：

- 订单号生成
- 订单主表写入
- 订单项写入
- 总金额写回

这样可以避免订单主表已创建但订单项部分失败的中间状态。

## 14. Django admin 设计

首版后台直接使用 Django admin，不开发独立商家后台。

### 14.1 Category admin

需要支持：

- 新增、编辑、启用停用分类
- 按排序值查看

### 14.2 Dish admin

需要支持：

- 维护分类、名称、描述、价格、图片地址、上架状态
- 快速筛选“可点/不可点”
- 按分类和排序值查看

### 14.3 Order admin

需要支持：

- 查看订单号、客户姓名、手机号、总金额、状态、创建时间
- 按状态筛选
- 按手机号、订单号搜索
- 在详情页查看订单项列表

### 14.4 OrderItem 展示

订单详情页应展示：

- 菜名快照
- 单价快照
- 数量
- 小计

订单项在后台主要用于查看历史，不建议在后台随意修改，避免破坏订单事实。

## 15. 前后端联调方式

开发阶段采用双服务运行：

- 前端：`npm run dev`
- 后端：`python manage.py runserver`

Vite 通过代理将 `/api` 请求转发给 Django。

这样前端代码中只需要请求相对路径：

- `/api/categories/`
- `/api/dishes/`
- `/api/orders/preview/`
- `/api/orders/`

好处如下：

- 避免前端写死开发环境地址
- 降低本地跨域处理复杂度
- 生产环境切换时前端接口路径更稳定

## 16. 页面交互流程

首版页面流程定义如下：

1. 用户进入首页。
2. 前端加载分类和菜品数据。
3. 用户选择菜品加入购物车。
4. 用户在购物车中调整数量。
5. 用户填写姓名、手机号和备注。
6. 前端可选调用预校验接口刷新准确总价。
7. 用户提交订单。
8. 后端创建订单并返回订单号。
9. 前端在当前页展示提交成功提示。

若提交失败：

- 保留当前购物车和表单内容
- 在页面显示具体错误原因
- 不清空用户已选内容

## 18. 实施顺序

推荐实施顺序如下：

1. 创建 Django 项目骨架与应用目录。
2. 定义模型、迁移和 admin。
3. 实现分类、菜品、订单预校验和正式下单接口。
4. 在 Vue 单页中插入点菜区、购物车区和提交表单。
5. 配置 Vite 代理并完成联调。
6. 补充测试与样式收口。

该顺序的目标是先把数据边界和接口边界锁定，再让前端围绕稳定接口实现交互，减少返工。

## 19. 后续扩展方向

如果首版稳定运行，后续可以按以下方向扩展：

- 增加桌号字段，支持堂食扫码点餐
- 增加取餐时间字段，支持到店自取
- 增加订单状态流转动作
- 增加用户历史订单查询
- 接入在线支付
- 将菜单和订单管理从 admin 升级为定制商家后台

这些能力都可以建立在本次首版的模型和接口基础上递进实现，不需要推翻整体架构。

## 20. 设计结论

本项目首版点菜功能采用以下最终方案：

- 继续使用现有 Vue 3 + Vite 单页前端
- 在当前单页内新增点菜区块，不新增独立点餐页
- 新建独立 Django 后端目录
- 使用 `catalog` 和 `orders` 两个主要业务应用承载菜单与订单
- 前端本地维护购物车
- 后端以数据库中的菜品状态和价格作为最终裁定
- 商家后台首版直接使用 Django admin

该方案实现成本适中、与当前项目结构兼容，并能满足轻量版点菜闭环的核心目标。
